## 1. Attack-surface inventory per agent: which files and stores change an agent's security posture, and how much benign churn each one has

### Takeaway
Every agent spreads its security posture across 5 to 10 places (user, project, local and managed settings; MCP configs; hook files; skills/plugins/extensions directories; instruction files; credential stores; shell profiles), and several of the most security-relevant keys live inside files the agents themselves rewrite constantly (`~/.claude.json` holds MCP servers and per-project trust flags; `.claude/settings.local.json` and Copilot's `permissions-config.json` accumulate "always allow" approvals; Copilot's `config.json` is internal state). A guard therefore needs per-agent parsers and key-level semantic diffs, with whole-file hashing reserved for low-churn files (hook files, managed policy, skills, shell profiles). Claude Code also hot-reloads `permissions`, `hooks` and `apiKeyHelper` mid-session, so a malicious edit takes effect without a restart.

#### 1b. Write and reload behaviour that drives churn and urgency
- Claude Code "watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to `permissions`, `hooks`, and credential helpers such as `apiKeyHelper`" — [Settings](https://code.claude.com/docs/en/settings)
- "When you change a setting in `/config`, Claude Code writes it to your settings files, and `/model` saves the value as your default for new sessions" (to `~/.claude/settings.json`) — [Settings](https://code.claude.com/docs/en/settings)
- `~/.claude.json` "Holds state that does not belong in settings.json: theme, OAuth session, per-project trust decisions, your personal MCP servers, and UI toggles"; `backups/` holds "Earlier versions of `~/.claude.json`, copied when Claude Code rewrites the file. Claude Code keeps the five newest" — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- Per-folder trust can be set by hand: "set `projects["<path>"].hasTrustDialogAccepted` to `true` in `~/.claude.json`" — [Permissions](https://code.claude.com/docs/en/permissions)
- Claude Code fires `ConfigChange` for settings-file changes detected during a session (matchers `user_settings`, `project_settings`, `local_settings`, `policy_settings`, `skills`) but "not for managed settings that arrive from MDM or the claude.ai console" — [Settings](https://code.claude.com/docs/en/settings), [Hooks](https://code.claude.com/docs/en/hooks)
- Copilot CLI's `config.json` is "internal application state that is managed automatically by the CLI"; saved approvals go to `permissions-config.json`, URL approvals to `allowedUrls` in `settings.json` — [Copilot CLI config dir](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference); [Allowing tools](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/allowing-tools)
- Gemini CLI saves trust decisions "in a central file (`~/.gemini/trustedFolders.json`)" — [Trusted folders](https://geminicli.com/docs/cli/trusted-folders)

#### 1c. What repository content takes effect before trust (relevant to "new repo cloned" alerts)
- Claude Code, for a folder never trusted in a `claude -p`/SDK run: hooks in settings files, the `env` block, helper commands such as `apiKeyHelper`, and a project skill's hooks and `allowed-tools` are "Used"; `.mcp.json` servers are "Connected without asking, approved or not"; "Workspace trust never gates a skill's `allowed-tools` in any session" — [Permissions](https://code.claude.com/docs/en/permissions)
- In interactive sessions, project `permissions.allow` and `additionalDirectories` wait for the trust dialog; project `.mcp.json` servers prompt; "A cloned repository can't approve its own servers" — [Permissions](https://code.claude.com/docs/en/permissions); [MCP](https://code.claude.com/docs/en/mcp)
- In February 2026 Check Point disclosed CVE-2025-59536 (repository settings auto-approving MCP servers), CVE-2026-21852 (`ANTHROPIC_BASE_URL` in project config sending "our full Anthropic API key, completely exposed in plaintext", before the trust prompt) and GHSA-ph6w-f82w-28w6 (project hooks) — [The Register, 2026-02-26](https://www.theregister.com/2026/02/26/clade_code_cves/)
- Codex: "Project-local hooks load only when the project `.codex/` layer is trusted" — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- Gemini CLI in an untrusted folder does not load `.gemini/settings.json` or project `.env`, does not connect MCP servers, and blocks extension installs — but trusted folders are off by default — [Trusted folders](https://geminicli.com/docs/cli/trusted-folders)
- Cursor: "Cursor supports workspace trust, but it's disabled by default" (`security.workspace.trust.enabled`) — [Cursor agent security](https://cursor.com/docs/agent/security)

### Inferences
- The guard's core data model should be "agent → scope → artifact → security-relevant keys", with each adapter declaring which keys are security-relevant. Alerting on any write to `~/.claude.json`, `.claude/settings.local.json`, Copilot `config.json`/`permissions-config.json`, Cursor `state.vscdb` or transcripts would fire many times per hour of normal use (researcher assessment based on the documented write behaviour above).
- The highest-value low-noise signals are: new or changed hook entries anywhere; new MCP server entries (any scope) or changed `command`/`args`/`url`; `hasTrustDialogAccepted` flipping to `true` for a folder the user never opened; new `allow` rules or `defaultMode: bypassPermissions`; `env` blocks that set base URLs or keys; new plugins/extensions/skills with executable content; managed-policy files appearing; credential files changing mode/owner or appearing in plaintext fallback locations.
- Because Claude Code hot-reloads hooks and `apiKeyHelper`, a guard that polls every few minutes is too slow to prevent abuse; it can only detect. Prevention requires an in-band control (Section 5).
- Repos are part of the attack surface: a guard should scan newly cloned or pulled projects for `.claude/`, `.mcp.json`, `.codex/`, `.cursor/`, `.github/hooks/`, `.gemini/`, `.agents/`, `opencode.json` and `.env` before the user opens them in an agent, especially for headless (`-p`) workflows where trust is not asked.

## 2. Change detection and attribution: can a user-space app know which process changed a config file?

### Takeaway
Detecting that a file changed is easy and cheap on every OS (FSEvents, inotify, ReadDirectoryChangesW), but none of those APIs say who wrote it. Reliable writer attribution needs privileged kernel-fed telemetry: Endpoint Security on macOS (Apple-granted entitlement, root, Full Disk Access, opaque approval with reported waits of about two months), privileged fanotify or auditd on Linux (root), and admin ETW or a signed minifilter on Windows. For a solo developer's MVP the realistic design is baseline + hash + semantic diff + time-window correlation with running agent processes ("changed while no agent was running"), which is exactly what the 2026 indie tool IAXT does without ES, and is what Fleet's `ai_tools` table does with content hashes.

### Cited Findings

#### macOS
- FSEvents granularity: "the granularity of notifications is at a directory level. It tells you *only* that something in the directory has changed, but does not tell you *what* changed"; the daemon "coalesces multiple notifications on a given directory if they occur in a short period of time"; Apple says it is "not designed for finding out when a particular file changes. For such purposes, the kqueues mechanism is more appropriate." The guide describes no way to identify the writing process — [Apple FSEvents Technology Overview](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html)
- Endpoint Security (ES) "is a C API for monitoring system events"; clients can "authorize pending events, or receive notifications of events that already occurred"; Apple's guidance is to "Develop your system extension with Endpoint Security and package it in an app that uses the System Extensions framework"; required entitlement `com.apple.developer.endpoint-security.client`; macOS 10.15+ — [Apple Endpoint Security](https://developer.apple.com/documentation/endpointsecurity)
- Client creation fails with `ES_NEW_CLIENT_RESULT_ERR_NOT_ENTITLED` ("isn't properly entitled"), `ERR_NOT_PERMITTED` ("isn't permitted", i.e. TCC/Full Disk Access) and `ERR_NOT_PRIVILEGED` ("The caller isn't running as root") — [es_new_client_result_t](https://developer.apple.com/documentation/endpointsecurity/es_new_client_result_t)
- Entitlement process, first-hand forum evidence:
  - A solo developer of an open-source "behavioral monitoring tool for detecting autonomous / AI-like activity locally" asked about approval chances; Apple DTS (Quinn) answered that approvers do not monitor the forums ("suck it and see"), that ES can be tested on one's own Mac with SIP disabled ("Don't disable SIP on a Mac that you care about"), and that "Capabilities are assigned to a specific team, so someone trying to build a product based on your open source would also have to apply for the ES capability" — [Apple Developer Forums 820718](https://developer.apple.com/forums/thread/820718)
  - A team building "agent identity infrastructure" got no acknowledgement email; DTS said the request system sends no ACK, status is visible in Request History, and "I'm not involved in the approval process, so I can't offer any insight into the timeline" — [Apple Developer Forums 841639](https://developer.apple.com/forums/thread/841639)
  - A developer of internal-company process-monitoring software reported waiting "almost 2 months" without approval — [Apple Developer Forums 743263](https://developer.apple.com/forums/thread/743263)
  - Post dates were not visible in the fetched copies of these threads.
- `eslogger` (Apple's CLI over ES): "must be run as super-user and requires the responsible process to have TCC Full Disk Access authorization"; emits JSON Lines; "By design, eslogger does not support any auth events"; "eslogger is NOT API in any sense. Do NOT rely on the structure or information emitted" — [eslogger(1)](https://keith.github.io/xcode-man-pages/eslogger.1.html)
- Objective-See BlockBlock uses "Apple's Endpoint Security Framework (to monitor for persistence)"; alerts show "the process name, pid, path, and arguments" with code-signing info, VirusTotal and "process ancestry"; Full Disk Access is "a prerequisite"; blocking means BlockBlock "will remove the item from the file system" (after-the-fact remediation); free, source on GitHub, macOS 10.15+, v2.5.2 — [Objective-See BlockBlock](https://objective-see.org/products/blockblock.html)
- osquery's macOS `es_process_file_events` table provides "File integrity monitoring events from EndpointSecurity including process context" with `pid`, `parent`, `path`, `filename`, `dest_filename`, `event_type` — [Fleet table docs: es_process_file_events](https://fleetdm.com/tables/es_process_file_events)
- IAXT (Show HN, 2026-07-08; free, closed source, macOS 13+): records AI-agent writes, process lifecycle and persistence with "no kernel extension, no system extension, and no Endpoint Security entitlement"; each action has an actor (`user / aiAgent / aiApp / system / unknown`) and a confidence where "High is direct PID ancestry or an exec-path match"; a filtering gate "throws away roughly 95% of OS noise (Spotlight, iCloud, Chrome temp, DerivedData)"; it "does not block anything" and cannot see reads; local SQLite at `~/Library/Logs/IAXT/events.db` — [HN: Show HN IAXT](https://news.ycombinator.com/item?id=48830666); [HN comment by the author](https://news.ycombinator.com/item?id=48830674)

#### Linux
- inotify: "The inotify API provides no information about the user or process that triggered the inotify event"; watches are not recursive; queues can overflow (`IN_Q_OVERFLOW`); `max_user_watches` caps watches per user — [inotify(7)](https://man7.org/linux/man-pages/man7/inotify.7.html)
- fanotify: unprivileged use exists since Linux 5.13 but is limited to inode marks and "A user will also not receive the pid that generated the event, unless the listening process itself generated the event"; `FAN_REPORT_PIDFD` (since 5.15) attaches a pidfd for "the process that was responsible for generating an event"; `FAN_CLASS_CONTENT` enables permission (blocking) decisions and is not available unprivileged — [fanotify_init(2)](https://man7.org/linux/man-pages/man2/fanotify_init.2.html)
- auditd watches: `-w path -p wa` triggers on writes and attribute changes — [auditctl(8)](https://linux.die.net/man/8/auditctl)

#### Windows
- `ReadDirectoryChangesW` returns `FILE_NOTIFY_INFORMATION` records with `NextEntryOffset`, `Action`, `FileNameLength`, `FileName` only, no process identity — [FILE_NOTIFY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-file_notify_information)
- ETW: "Only users with administrative privileges, users in the Performance Log Users group, and services running as LocalSystem, LocalService, NetworkService can control event tracing sessions ... Only users with administrative privileges and services running as LocalSystem can control an NT Kernel Logger session" — [StartTraceW](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/nf-evntrace-starttracew)
- A file-system minifilter is a kernel driver; attestation signing requires "an extended validation (EV) code signing certificate" and registration in the Hardware Developer Program, and "Attestation signed drivers that target retail audiences aren't published on Windows Update" — [Microsoft: attestation signing](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)

#### Vendor-native, in-band signals
- Claude Code `ConfigChange` hook fires on settings/skills changes during a session and can block them ("Blocks the configuration change from taking effect (except `policy_settings`)") — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- Codex records hook trust "against the hook's current hash, so new or changed hooks are marked for review and skipped until trusted" — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- Gemini CLI "fingerprints project hooks. If a hook's name or command changes (for example, via `git pull`), it is treated as a new, untrusted hook" — [Gemini CLI hooks](https://geminicli.com/docs/hooks)
- Claude Code keeps `~/.claude/sessions/` lock files for running sessions (removed on exit) — [.claude directory](https://code.claude.com/docs/en/claude-directory)

### Inferences
- Realistic MVP attribution ladder (researcher design, consistent with IAXT and BlockBlock evidence):
  1. Watch with FSEvents (file-level events flag) / inotify / ReadDirectoryChangesW; on each event, re-read and semantically diff the file against the baseline.
  2. At event time, snapshot running processes (no privileges needed to list processes and their executable paths for the same user) and agent session state (Claude `sessions/` lock files, hook-reported SessionStart/End, Codex/Copilot session dirs' mtimes).
  3. Classify: "expected writer present" (e.g. `~/.claude.json` changed while a `claude` process ran and the diff touched only benign keys) vs "security key changed while no agent/IDE that owns the file was running" (high severity) vs "security key changed while the owning agent was running" (medium; could be the agent itself acting on a prompt injection, or a user action).
  4. Content signatures: agents write files in recognisable ways (key ordering, formatting, backup files appearing in `~/.claude/backups/`); a hand-edited or script-edited file often differs. This is a heuristic only.
- This yields "probable writer" with a confidence label, never proof. Malware running as the same user can time its writes to coincide with agent activity, so the heuristic is defeatable by a targeted attacker; it is adequate for catching accidents, sloppy supply-chain payloads and agent self-modification.
- ES is the only route to true attribution and to blocking writes on macOS, but it costs: Apple approval with no SLA (one report of about two months), a root system extension that users must approve, Full Disk Access, and a product that is now "security software" in support terms. It should be a later "Pro" component, applied for early since the wait is long, with the core product working without it.
- Linux is the easiest platform for true attribution if the user accepts a root helper (privileged fanotify with `FAN_REPORT_PIDFD`, or auditd watches); unprivileged fanotify gives nothing beyond inotify for attribution.
- Windows true attribution needs an elevated service consuming ETW file events; a minifilter is out of reach for an individual (EV certificate, Microsoft signing, kernel-driver liability).
- CPU/battery: FSEvents coalescing and a latency parameter, plus watching only a few dozen known directories (not the whole home folder), keep cost low; the heavier cost is re-parsing large hot files (`~/.claude.json`) on every rewrite, which argues for debouncing (e.g. 1 to 2 s) and hashing before parsing.

### Gaps
- Exact ES event names for file writes (`NOTIFY_WRITE`, `NOTIFY_CLOSE` with modified flag, `AUTH_OPEN`, `NOTIFY_BTM_LAUNCH_ITEM_ADD`) and whether a plain root LaunchDaemon (rather than a system extension) can hold the entitlement for distribution were not confirmed in fetched Apple pages.
- No first-hand report of an individual developer being granted or refused the ES entitlement in 2026 was found; HN search found only a maker who deliberately avoided ES.
- Whether `fs_usage` or Unified Logging can attribute writes without ES was not researched; `fs_usage` requires root (not verified in this pass).
- Sysmon (Windows) and eBPF (Linux) as attribution sources were not researched.
- IAXT's exact mechanism for "direct PID ancestry" without ES is not described in the sources.

## 3. Secret detection in agent configs: engines, licences, fields to scan, and safe remediation

### Takeaway
Embeddable local engines exist under permissive licences (Betterleaks and gitleaks MIT in Go; Kingfisher Apache-2.0 in Rust; detect-secrets Apache-2.0 in Python); TruffleHog is AGPL-3.0 and ggshield needs GitGuardian's API, so neither suits embedding in a closed local app. Every agent now offers an indirection mechanism (Claude `${VAR}` expansion and `headersHelper`, VS Code `inputs`, Codex `bearer_token_env_var`, Cursor `${env:...}`, Devin `${file:...}`, Copilot keychain-backed MCP secret placeholders, 1Password `op run`), but they differ in which fields they cover and some deliberately blank credential-looking variables, so automated rewriting is risky; guided, per-agent fixes with backups and a post-fix connectivity check are the safe pattern.

### Cited Findings

#### Engines and licences

|---|---|---|---|---|---|
| Betterleaks | MIT | Pure Go | Successor to gitleaks; rule-defined validation in CEL; vendor claim of "98.6% recall vs 70.4% with entropy on the CredData dataset" | Launched 2026-03-15 by Zach Rice (Aikido-sponsored) | [BleepingComputer](https://www.bleepingcomputer.com/news/security/betterleaks-a-new-open-source-secrets-scanner-to-replace-gitleaks/) |
| gitleaks | MIT | Go library (`pkg.go.dev/github.com/gitleaks/gitleaks/v8`) | TOML rules with regex, entropy, keywords, allowlists; `dir` and `stdin` modes; `gitleaks:allow`, `.gitleaksignore`, baselines | "feature complete ... #### Indirection and storage mechanisms per agent (what a fix can target)
- Claude Code `.mcp.json`: `${VAR}` and `${VAR:-default}` expand in `command`, `args`, `env`, `url`, `headers` — [Claude Code MCP](https://code.claude.com/docs/en/mcp)

- Claude Code sandbox credential masking: `sandbox.credentials` `mask` entries show sandboxed commands a per-session "sentinel" and the sandbox proxy substitutes the real value only toward `injectHosts`; it needs `network.tlsTerminate`; masking settings are honoured only from user settings, managed settings and `--settings`, not repository files; on macOS, file masking falls back to blocking the file — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- VS Code: `inputs` with `"type": "promptString"`, `"password": true`, referenced as `${input:id}`; "The value is then securely stored for subsequent use"; `envFile` loads a dotenv file — [VS Code MCP servers](https://code.visualstudio.com/docs/copilot/customization/mcp-servers)
- Codex MCP: `bearer_token_env_var`, `http_headers`, `env` per `[mcp_servers.<id>]`; `mcp_oauth_credentials_store` controls OAuth token storage — [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli); [Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)
- Codex shell environment: with `ignore_default_excludes` true (the default), "Codex doesn't automatically remove variable names containing `KEY`, `SECRET`, or `TOKEN`" from the environment passed to commands — [Codex advanced config](https://learn.chatgpt.com/docs/config-file/config-advanced)
- Cursor: `${env:NAME}`, `${userHome}`, `${workspaceFolder}` interpolation in `mcp.json` — [Cursor MCP](https://cursor.com/docs/context/mcp)
- Devin Desktop (Windsurf): `${env:VAR}` and `${file:/path}` — [Devin Desktop MCP](https://docs.devin.ai/desktop/cascade/mcp)
- Copilot CLI: `mcp-secrets/` is "Local fallback storage and index for MCP secret placeholders" used when keychain-backed storage is unavailable — [Copilot CLI config dir](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)
- Gemini CLI: `security.environmentVariableRedaction` setting; `.env` files auto-loaded (see Section 1) — [Gemini CLI configuration](https://geminicli.com/docs/reference/configuration)
- 1Password: secret references `op://vault/item/field` in env vars or `.env` files; `op run` "loads the specified secrets, then runs the provided command in a subprocess with the secrets made available as environment variables only for the duration of the process", and masks output — [1Password CLI: secrets in environment variables](https://www.1password.dev/cli/secrets-environment-variables)
- Claude Desktop extensions store values marked sensitive in the OS keychain — [Anthropic: Desktop Extensions](https://www.anthropic.com/engineering/desktop-extensions)

### Inferences
- Engine choice: for a Rust core, Kingfisher (Apache-2.0, embeddable) or porting Betterleaks/gitleaks rule sets (MIT, TOML/regex, attribution required) are licence-clean; TruffleHog's AGPL would impose copyleft on a distributed derivative, so at most shell out to a user-installed binary. Live verification (calling GitHub/Stripe/OpenAI with the found key) should be off by default: it transmits the secret, can trip provider abuse detection, and contradicts a local-only promise.
- Fields to scan per server entry: `env` values, `headers`/`http_headers` values, `args` (e.g. `--token=`, `--api-key`), `url` query strings and userinfo (`https://user:pass@`, `?key=`), database URLs (`postgres://user:pass@`), inline JSON blobs in args, `command` strings (e.g. `sh -c "TOKEN=... npx ..."`), plus `.env` files the agents auto-load (Gemini CLI) and `env` blocks in agent settings. Keys that are references (`${VAR}`, `${input:...}`, `${env:...}`, `op://`, `${file:...}`, `bearer_token_env_var`) should be recognised and not flagged.
- False-positive control: per-finding fingerprints stored in the guard's baseline ("acknowledged"), plus provider-format validation (prefix + checksum, e.g. GitHub token formats) before entropy fallbacks. Localhost URLs and documented placeholder values should be downgraded.
- Automated rewriting is unsafe as a default because: (1) the agent may rewrite the same file concurrently (`~/.claude.json`); (2) GUI-launched agents on macOS do not necessarily inherit shell-profile variables, so moving a secret to `export X=...` in `~/.zshrc` can silently break servers started by IDEs (researcher inference, not verified here); (3) Claude Code blanks some credential variables in remote URLs/headers and strips credential-looking variables from project `headersHelper` environments, so a naive `${GITHUB_TOKEN}` rewrite may send an empty header; (4) storing the secret in the shell profile just moves it to another plaintext file. A safe flow is: show the finding → offer agent-specific options (Claude: `headersHelper` script reading the Keychain via `security find-generic-password`, or `${VAR}` with the variable injected by `op run`; VS Code: `inputs`; Codex: `bearer_token_env_var`) → write via vendor CLI where possible (`claude mcp add`, `codex mcp add`, `copilot mcp add`) or an atomic write with backup → re-check that the server still connects → recommend rotating the exposed key (it already sat in plaintext and possibly in transcripts and backups).
- Remediation must also clean secondary copies: `~/.claude/backups/` keeps old `~/.claude.json` copies, and transcripts can contain secrets that passed through tools (Section 1).

### Gaps
- Betterleaks rule count, config compatibility with gitleaks and library API were not confirmed (only press coverage was read).
- Whether Claude Code's blanking applies to arbitrary user variables (e.g. `GITHUB_TOKEN`) or only to a fixed list could not be determined from the excerpt; needs testing.
- Exact Codex field names `env_vars` and `env_http_headers` for MCP servers were not confirmed.
- Nosey Parker, secretlint and ripsecrets were not evaluated.
- VS Code's storage backend for `inputs` (OS keychain via SecretStorage) is not stated on the page read.

## 4. "What can it execute": static capability analysis of hooks, skills, plugins and MCP servers

### Takeaway
Each agent has many code-execution points beyond MCP servers (command/HTTP hooks, status lines, credential helpers, `headersHelper`, plugin `bin/` and `monitors`, LSP servers, OpenCode plugins loaded in-process, Gemini extensions), and none of the packaging standards (MCPB `manifest.json`, MCP Registry `server.json`) declares filesystem or network permissions, so "what can it do" must be inferred from commands, scripts and package specs. Listing a stdio server's tools requires running it; the MCP spec itself says clients must show the exact command and should sandbox, and Snyk's agent-scan asks consent per server before launching. A guard can do useful static analysis without executing anything and should defer dynamic tool listing to an explicit, sandboxed action.

- MCP spec: local servers are "binaries that are downloaded and executed on the same machine"; clients offering one-click setup "MUST" show "the exact command that will be executed, without truncation" and require approval, and "SHOULD" highlight dangerous patterns (`sudo`, `rm -rf`, network operations), "Execute MCP server commands in a sandboxed environment with minimal default privileges" and use "platform-appropriate sandboxing technologies (containers, chroot, application sandboxes, etc.)" — [MCP security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)
- Snyk Agent Scan (formerly Invariant mcp-scan; Apache-2.0; 3.1k stars) discovers MCP servers and skills for 13 agents including Claude Code, Cursor, VS Code, Copilot, Windsurf, Gemini CLI, OpenCode, Antigravity and Codex; it "connects to servers and retrieves tool descriptions", starting "stdio MCP servers by executing the commands in the config"; by default it prompts before contacting each server; background scans do not run stdio servers unless `--dangerously-run-mcp-servers`; it "sends ... MCP server configurations and signatures, tool names and descriptions, and skill content" for analysis with secrets redacted; v0.6+ detects 14 risks (prompt injection, untrusted content, private data exposure, destructive capabilities; skill injection, suspicious downloads, malicious code, insecure credential handling, secrets) — [Snyk agent-scan](https://github.com/snyk/agent-scan)
- Cisco MCP Scanner (Apache-2.0; 1.1k stars): YARA analyzer (no keys), LLM-as-judge (needs an LLM API key), Cisco AI Defense API, and behavioural code analysis of server source in 10 languages (Python, TypeScript, JavaScript, Go, Java, Kotlin, C#, Rust, Ruby, PHP); live scanning of remote servers or static/offline scanning of JSON and of well-known client configs (Windsurf, Cursor, Claude, VS Code) — [Cisco mcp-scanner](https://github.com/cisco-ai-defense/mcp-scanner)
- Cisco Skill Scanner (Apache-2.0; 2.5k stars): static/YARA, AST dataflow, pipeline taint, LLM semantic analysis, VirusTotal hashes; "does not execute skill code"; "A scan that returns no findings does not guarantee that a skill is free of all threats" — [Cisco skill-scanner](https://github.com/cisco-ai-defense/skill-scanner)

### Inferences
- Static capability model the guard can compute without running anything (researcher design):
  - Launcher class: `npx`/`bunx`/`pnpm dlx` (npm), `uvx`/`pipx` (PyPI), `docker run` (OCI; check `--privileged`, `-v` host mounts, `--network host`), absolute binary path (hash + code signature on macOS), interpreter + local script (hash script), remote URL (host, scheme, auth type).
  - Pinning: package spec with exact version vs range vs `@latest`/no version (rug-pull exposure); `-y` auto-install flags; docker tags vs digests.
  - Provenance: match the package against the MCP Registry `server.json` (which requires pinned versions and marks secret env vars) and npm/PyPI metadata; flag typosquats of popular servers.
  - Capability hints: env var names (e.g. `GITHUB_TOKEN` implies GitHub write access depending on token scopes), args such as filesystem roots (`/`, `~`), `--allow-write`, database URLs, and declared `tools` in MCPB manifests (readable without launching).
  - Hooks and helpers: parse command strings into argv/shell AST; resolve referenced scripts and hash them; flag network egress (`curl`, `wget`, `nc`), credential-file reads (`~/.ssh`, `~/.aws`, Keychain `security` commands), obfuscation (`base64 -d | sh`, `eval`), downloads-then-exec, writes to agent configs (self-modification), and HTTP hooks posting to non-loopback URLs. Map each hook to its event/matcher so the UI can say "runs before every Bash command in every project".
  - Skills: list bundled scripts and their static red flags (reuse Cisco skill-scanner-style rules), Claude `allowed-tools` breadth (e.g. `Bash` unrestricted), and frontmatter hooks.
- Dynamic tool listing should be an explicit per-server user action, run with the exact command shown (as the MCP spec requires of clients), inside a sandbox: on macOS a Seatbelt profile (the same mechanism Claude Code and Codex use, though `sandbox-exec` is deprecated) denying network except the registry and writes outside a temp dir; or a container where Docker is present. Even sandboxed, a server can fetch remote tool descriptions later (rug pull), so the guard should hash the tool list and re-check periodically only for servers the user opts in.
- Remote servers' OAuth scopes are visible only during the flow or inside the stored token; reading those tokens touches credential stores. Inventory should show host, auth type (OAuth vs static header) and whether a static secret is present, and stop there.

### Gaps
- No standard permissions manifest for MCP servers or skills was found in MCPB, the MCP Registry, or Agent Skills; whether Docker's MCP Catalog metadata declares network/filesystem needs, and the exact Docker gateway flags (`--verify-signatures`, `--block-secrets`, `--block-network`), were not confirmed.
- Socket's package analysis for MCP servers was not researched.
- Whether VS Code offers built-in sandboxing for stdio MCP servers in 2026 could not be confirmed (the MCP page read mentions none).

## 5. Runtime enforcement: what a guard can block versus only warn about

### Takeaway
All six target agents now expose pre-execution hooks that can deny tool calls, which a guard can install to enforce policy (block a dangerous command, a read of `~/.ssh`, a call to a flagged MCP server, or any action once a budget is exhausted). But hooks are cooperative: they live in user-writable files, fail open on timeouts in most agents (Cursor fails open on crashes by default unless `failClosed` is set), can be disabled by settings precedence, and are explicitly called "a useful guardrail, not a complete enforcement boundary" by OpenAI. Hard enforcement exists only where the guard controls an OS boundary (ES/fanotify, root) or where admin-installed managed policy pins hooks.

### Cited Findings

#### Ways hooks can be switched off or overridden (Claude Code)
- "set `"disableAllHooks": true` in your settings file. Claude Code reads the value left after settings precedence applies, so a `"disableAllHooks": false` in a project's `.claude/settings.json` overrides a `true` in your user settings"; `--settings '{"disableAllHooks": true}'` turns hooks off for one run — [Claude Code hooks](https://code.claude.com/docs/en/hooks)
- `allowManagedHooksOnly` (managed) blocks user, project, local and plugin hooks; it is a "lock" that "Applies the strictest value any source sets" — [Claude Code hooks](https://code.claude.com/docs/en/hooks); [Managed settings](https://code.claude.com/docs/en/managed-settings)

#### OS sandboxes and their limits

#### Gateways
- MCP gateways that front servers (Docker MCP Gateway, MCP Router, ToolHive) can filter tools centrally, but only for servers routed through them — [Docker MCP Gateway docs](https://docs.docker.com/ai/mcp-catalog-and-toolkit/mcp-gateway/); earlier note section 7

### Inferences
- Enforce vs warn (researcher assessment):
  - Enforceable (cooperative): deny specific tool calls, file reads (e.g. `Read(~/.ssh/**)` via Claude deny rules; Cursor `beforeReadFile`), MCP calls to flagged servers (Cursor `beforeMCPExecution`, Claude matcher `mcp__server__*`), prompts once a spend cap is hit (`UserPromptSubmit`/`beforeSubmitPrompt`), and mid-session settings changes in Claude Code (`ConfigChange` hook can block user/project/local/skills changes).
  - Enforceable for real only with admin rights: Claude managed settings (`allowManagedHooksOnly`, deny rules, `disableBypassPermissionsMode`), Cursor enterprise `hooks.json`, Copilot `policy.d`, Gemini system override settings. A guard installer could offer an "admin mode" that writes these system files once with the user's password; the user (as local admin) can still undo it.
  - Warn-only: anything that happens outside a hooked agent (malware editing configs, a different agent, Cursor cloud agents, Copilot's cloud agent), account-side billing settings, and remote MCP servers' server-side behaviour.
- Hook-based guards must be designed for fail-open defaults: keep the decision path local and fast (an HTTP hook to `127.0.0.1` or a tiny binary reading a memory-mapped policy), set Cursor `failClosed: true` for security hooks, and treat a missing guard response as "ask" where the agent supports it.
- A malicious repository could try to neutralise a user-level guard hook through settings precedence (e.g. a project `disableAllHooks: true`); whether trust gating prevents this was not verified and should be tested before claiming protection (see Gaps).
- The guard's own hook entries become attack surface: they should be minimal, point to a signed binary in the app bundle, and be re-verified by the watcher (Section 2) so removal or tampering is detected.

### Gaps
- Whether hooks fire under `--dangerously-skip-permissions` (Claude Code), `--yolo`/`--dangerously-bypass-approvals-and-sandbox` (Codex), Cursor auto-run/"Run Everything", Copilot `--yolo` and Gemini YOLO is not stated explicitly in any doc read; for Claude Code and Codex the presence of `permission_mode` in hook input implies they do.
- Whether a project-level `disableAllHooks: true` in an untrusted repository disables user-level hooks was not determined.
- VS Code agent-mode hooks (if any) were not found on the pages read.
- Hook latency overhead was not measured by any source found.

## 6. Billing lint and spend stops

### Takeaway
Most billing foot-guns are visible locally and safely: stray `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN`/`apiKeyHelper` outranking a Claude subscription (with documented precedence), `OPENAI_API_KEY`/`CODEX_API_KEY`/custom providers for Codex, `GH_TOKEN`-style overrides for Copilot, `GEMINI_API_KEY` and auto-loaded `.env` files for Gemini CLI, and base-URL variables pointing at unknown hosts (which is also the CVE-2026-21852 exfiltration pattern). Account-side switches (Claude usage credits set to "unlimited" or auto-reload, ChatGPT/Codex credits auto-reload, Cursor on-demand limits, Copilot overage budgets, OpenAI hard limits) are not exposed through any personal-account API, so a guard can only read them through undocumented cookie-based endpoints (terms risk) or ask the user to confirm them in a checklist. Spend stops are possible only as cooperative hooks on estimated spend, Claude's print-mode `--max-budget-usd`, or vendor-side limits.

### Cited Findings
- Claude Code credential precedence: (1) cloud provider env (`CLAUDE_CODE_USE_BEDROCK`/`_VERTEX`/`_FOUNDRY`), (2) `ANTHROPIC_AUTH_TOKEN`, (3) `ANTHROPIC_API_KEY` ("In interactive mode, you are prompted once to approve or decline the key, and your choice is remembered ... In non-interactive mode (`-p`), the key is always used when present"), (4) `apiKeyHelper`, (5) `CLAUDE_CODE_OAUTH_TOKEN`, (6) Anthropic profile/federation credentials, (7) subscription OAuth from `/login` — [Claude Code authentication](https://code.claude.com/docs/en/authentication)

| B17 | Spend stop: estimated session/day spend above user cap | Local usage estimates (earlier note section 1) | Install `UserPromptSubmit`/`PreToolUse` (Claude, Codex), `beforeSubmitPrompt`/`preToolUse` (Cursor), `preToolUse` (Copilot), `BeforeAgent`/`BeforeTool` (Gemini) hooks that deny when over cap | Hard (cooperative, estimate-based, fail-open on timeouts) | None |

### Inferences
- B1 to B8 and B12 to B14 make a strong free tier: they are local, sanctioned or harmless, and explain real surprise bills. The account-side checks (B9 to B11, B15, B16) are best delivered as a guided checklist with deep links and a "last confirmed" date, not scraping.
- Base-URL checks (B6) double as security checks and should run on repository content at clone/pull time, given CVE-2026-21852.
- Spend stops built on hooks are a "seatbelt": they stop the next prompt or tool call, not a response already streaming, and depend on estimated prices; vendor-side caps (Cursor spend limits, OpenAI hard limits, Claude credit limits, OpenRouter key limits) are the only hard stops and the guard's job is to make sure they are set.

### Gaps
- Codex auth precedence between a stored ChatGPT login and env API keys is only documented by a secondary source; GitHub issues it cites were not read.
- Gemini CLI precedence between OAuth and `GEMINI_API_KEY`, and Copilot's default overage budget for individuals, were not documented on the pages read.
- Whether Claude Code persists the API-key approval choice (and under which `~/.claude.json` key) was not confirmed.
- Programmatic configuration of OpenAI spend limits (Admin API fields) was not documented on the page read.

## 7. Self-protection, privacy and trust

### Takeaway
Against malware running as the same user, a non-privileged guard can be killed and its files edited, so the realistic goal is tamper-evidence (detect and report that the guard or its baseline was altered), not tamper-proofing. The guard itself reads the most sensitive material on a developer's machine (agent configs, credential-file metadata, possibly transcripts), so trust posture (local-only processing, no telemetry, open-source core, minimal Keychain access) is a product requirement, as competitors already advertise.

### Cited Findings
- `SMAppService` (macOS 13+) registers LoginItems, LaunchAgents and LaunchDaemons bundled inside the app as "a replacement for installing property lists in `~/Library/LaunchAgents` or `/Library/LaunchAgents`" and `/Library/LaunchDaemons` — [Apple SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)
- ES clients need root and Full Disk Access (see Section 2); BlockBlock requires Full Disk Access — [es_new_client_result_t](https://developer.apple.com/documentation/endpointsecurity/es_new_client_result_t); [BlockBlock](https://objective-see.org/products/blockblock.html)
- Keychain prompts are tied to code signatures: access-control lists do not make "an unstable or changed code signature satisfy the item's access-control list"; CodexBar's policy is that background work fails closed and foreign items need "explicit, default-off consent" — [CodexBar KEYCHAIN_FIX.md](https://raw.githubusercontent.com/steipete/CodexBar/main/docs/KEYCHAIN_FIX.md)
- Transcripts are plaintext and contain tool output including any printed secrets — [.claude directory](https://code.claude.com/docs/en/claude-directory)
- Privacy postures of comparable tools: Agent Sessions "No telemetry, analytics, remote logging" — [Agent Sessions](https://github.com/jazzyalex/agent-sessions); IAXT "no telemetry or cloud connectivity" with a local SQLite store — [HN comment](https://news.ycombinator.com/item?id=48830674); GitGuardian's inventory uploads configuration metadata and "hashed fingerprints" of secrets, keeping files and transcripts local unless `--activity` is used — [GitGuardian agent and MCP inventory](https://docs.gitguardian.com/endpoint-protection/agent-and-mcp-inventory); Snyk Agent Scan sends tool descriptions and skill content to Snyk with secrets redacted and says it "does not store or log any usage data" — [Snyk agent-scan](https://github.com/snyk/agent-scan)
- Claude Code itself treats `.claude` and shell rc files as protected paths not auto-approved for agent writes (except in bypass mode) — [Permission modes](https://code.claude.com/docs/en/permission-modes)

### Inferences
- Tamper-evidence design (researcher proposal):
  - Store the baseline in the app's container/Application Support, with an HMAC over each record keyed by a random secret kept in a Keychain item created by the guard (ACL bound to the guard's signature, so other processes trigger a prompt rather than read silently). A baseline whose HMAC fails is reported as tampered.
  - Run the watcher as a LaunchAgent registered via `SMAppService` with KeepAlive-style relaunch; on each start, compare "last heartbeat" with uptime and report gaps ("guard was not running from 14:02 to 14:40").
  - Watch the guard's own hook entries in each agent and its LaunchAgent plist; removal is itself an alert.
  - Optional off-device anchor: let the user export a signed baseline digest (e.g. to a gist or email) so a full wipe is detectable later.
  - Without ES (`AUTH_SIGNAL`-style protection was not verified here) or root, the guard cannot prevent being killed; say so plainly.
- Privileges to request: none for reading dotfiles in the home folder (researcher expectation, consistent with CodexBar treating Full Disk Access as optional for Safari cookies only); avoid reading other apps' Keychain items entirely (metadata via file existence is enough for billing lint); Full Disk Access only if/when the ES component ships.
- Privacy defaults: parse configs locally; never transmit file contents; transcripts off by default (opt-in secret scan only); no live secret verification; no telemetry; open-source the core scanner and rules so security reviewers can audit what the guard reads. Signed and notarised builds with reproducible release notes; Sparkle/Tauri updater with signature verification, because an auto-updating security tool with broad file read is itself a high-value supply-chain target.
- CPU/battery: watch only enumerated directories; debounce; hash before parse; cap re-scan frequency of large hot files; skip transcripts. IAXT's reported 95% noise drop from path gating shows that unfiltered watching produces mostly OS noise.

### Gaps
- Apple documentation on `SMAppService` approval UX (`requiresApproval`) and launchd `KeepAlive` semantics was not captured.
- Whether ES can protect a client from `kill` by same-user processes (signal authorisation) was not confirmed.
- No source quantified CPU/battery cost of FSEvents watchers for this workload.

## 8. Prior art: how existing tools implement inventory, scanning and attribution

### Takeaway
The "inventory + scan" half of the guard idea already exists in enterprise tools (Fleet's `ai_tools` osquery table, GitGuardian's `ggshield ai discover`, 1Password Device Trust "AI Insights", Knostic Kirin) and in free scanners (Snyk Agent Scan, Cisco MCP and skill scanners), while the "attribution" half exists in free macOS tools (Objective-See BlockBlock with ES; IAXT without ES). Vendors are also building change control into the agents themselves (Codex hook hashing, Gemini hook fingerprinting, Claude `ConfigChange`, `claude plugin validate` credential warnings). No found tool combines local, consumer-grade cross-agent change monitoring, secret migration and billing lint for individuals.

### Cited Findings
- Fleet `ai_tools` table (fleetd, not core osquery; macOS, Windows, Linux): "Surfaces AI tools on the host: MCP servers, AI agent CLIs, AI desktop apps, IDE plugins, live AI/MCP network sockets, agent instruction files, and browser extensions"; enumerates all home directories; columns include `type`, `path`, `endpoint`, `pid`, `running`, `risk_flags`, `confidence`, `evidence`, and `sha256` "Content hash for change detection" — [Fleet ai_tools](https://fleetdm.com/tables/ai_tools)
- osquery `es_process_file_events` gives ES-based file-integrity events with process context on macOS — [Fleet table docs](https://fleetdm.com/tables/es_process_file_events)
- GitGuardian AI agents and MCP inventory: inventories agents (Claude Code, Cursor, Codex named), MCP servers, whether AI hooks are installed, subscription email, and "hashed fingerprints of detected secrets"; deployed as "a scheduled MDM job" running `ggshield ai discover`; Business/Enterprise plans; "does not block"; blocking comes from separate AI hooks — [GitGuardian docs](https://docs.gitguardian.com/endpoint-protection/agent-and-mcp-inventory); [ggshield](https://github.com/GitGuardian/ggshield)
- 1Password Device Trust added (2026-08-28) "AI Insights, giving you visibility into how AI tools are used across your organization" and an MCP server for querying device data — [1Password Device Trust what's new](https://support.1password.com/device-trust-whats-new/)
- Knostic "Kirin AI Coding Safety": "Automatically scan dependencies, validate MCP servers, and enforce guardrails"; "blocks rogue servers"; deployment details and pricing not stated — [Knostic](https://www.knostic.ai/coding-assistants-agents-mcp)
- Snyk Agent Scan, Cisco MCP Scanner, Cisco Skill Scanner: see Section 4 — [Snyk agent-scan](https://github.com/snyk/agent-scan); [Cisco mcp-scanner](https://github.com/cisco-ai-defense/mcp-scanner); [Cisco skill-scanner](https://github.com/cisco-ai-defense/skill-scanner)
- Objective-See BlockBlock (ES; process name, pid, path, args, signing, ancestry; removal on block) — [BlockBlock](https://objective-see.org/products/blockblock.html)
- IAXT (no ES; actor/confidence attribution; noise gating; logs writes not contents; no blocking) — [HN Show HN](https://news.ycombinator.com/item?id=48830666)
- Vendor-native controls: Codex hash-based hook trust ([Codex hooks](https://learn.chatgpt.com/docs/hooks)); Gemini hook fingerprinting ([Gemini hooks](https://geminicli.com/docs/hooks)); Claude `ConfigChange` hook, `/hooks` browser with source of each hook, `allowManagedHooksOnly` ([Claude Code hooks](https://code.claude.com/docs/en/hooks)); `claude plugin validate` literal-credential warnings ([Plugins reference](https://code.claude.com/docs/en/plugins-reference)); Claude sandbox credential masking ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing))
- ToolHive/MCPM/cc-switch rewrite agent configs as managers (relevant as both prior art for adapters and as "benign writers" a guard must recognise) — earlier note section 7 ([cc-switch](https://github.com/farion1231/cc-switch), [ToolHive client compatibility](https://docs.stacklok.com/toolhive/reference/client-compatibility))

### Inferences
- Enterprise vendors have validated the problem (inventory, secrets in configs, hooks status) but sell to security teams via MDM; Snyk and Cisco give scanners away. A consumer/indie guard competes on local-first UX, change history ("what changed since yesterday and who probably did it"), guided secret migration and billing lint, not on detection depth.
- Fleet's `sha256` column and IAXT's gating confirm "hash + context" as the accepted non-ES approach.
- Config managers (cc-switch, ToolHive, MCPM) are legitimate writers; the guard needs an allowlist of known manager processes and their write patterns to avoid alert fatigue.

### Gaps
- Kolide/1Password Device Trust check catalogue for AI agents (specific checks, if any) was not found beyond "AI Insights".
- Socket, Pillar, Lasso, Prompt Security and similar commercial MCP/agent security products were not researched.
- No open-source "AI agent inventory" script beyond these tools was found in this pass.

## 9. Cross-platform differences that matter

### Takeaway
Paths, policy stores, credential stores, sandboxes and attribution primitives all differ per OS, and WSL adds a second Linux filesystem with its own agent installs; macOS-first with an OS-abstracted adapter layer is the right sequencing, and Windows attribution should be scoped to "detect and diff" only.

### Cited Findings
- Claude Code: credentials `%USERPROFILE%\.claude\.credentials.json` on Windows, plaintext `~/.claude/.credentials.json` on Linux, Keychain on macOS — [Claude Code authentication](https://code.claude.com/docs/en/authentication); managed policy `C:\Program Files\ClaudeCode\`, `HKLM`/`HKCU\SOFTWARE\Policies\ClaudeCode`, `/etc/claude-code/` on Linux/WSL; "On WSL, `/etc/claude-code` is user-writable as well"; `wslInheritsWindowsSettings` makes WSL read the Windows policy chain — [Managed settings](https://code.claude.com/docs/en/managed-settings)
- Claude Code sandbox: Seatbelt (macOS), bubblewrap + socat (Linux/WSL2; Ubuntu 24.04+ AppArmor may block user namespaces), none on native Windows — [Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)
- Codex sandbox: Seatbelt, bubblewrap, native Windows sandbox — [Codex sandboxing](https://learn.chatgpt.com/docs/sandboxing)
- Cursor enterprise hooks: `/Library/Application Support/Cursor/`, `/etc/cursor/`, `C:\ProgramData\Cursor\` — [Cursor hooks](https://cursor.com/docs/agent/hooks)
- Copilot CLI: hooks `%USERPROFILE%\.copilot\hooks\` on Windows; policy `C:\ProgramData\GitHub\Copilot\policy.d\`; tokens in Keychain (macOS), Credential Manager (Windows), libsecret (Linux) with plaintext `~/.copilot/config.json` fallback — [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-configuration); [Authenticate Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli)
- Gemini CLI system files under `/Library/Application Support/GeminiCli/`, `/etc/gemini-cli/`, `C:\ProgramData\gemini-cli\` — [Gemini CLI configuration](https://geminicli.com/docs/reference/configuration)
- Codex hooks support Windows via `commandWindows` and `windows_managed_dir` — [Codex hooks](https://learn.chatgpt.com/docs/hooks)
- Claude Desktop config `%APPDATA%\Claude\claude_desktop_config.json`; Devin `%APPDATA%\devin\mcp_config.json`; Anthropic profiles `%APPDATA%\Anthropic` — [MCP: connect local servers](https://modelcontextprotocol.io/docs/develop/connect-local-servers); [Devin Desktop MCP](https://docs.devin.ai/desktop/cascade/mcp); [Claude Code authentication](https://code.claude.com/docs/en/authentication)
- Attribution primitives: FSEvents (no writer), ES (entitled root client); inotify (no writer), fanotify (writer only when privileged); ReadDirectoryChangesW (no writer), ETW (admin), minifilter (EV-signed driver) — Section 2 sources

### Inferences
- The adapter table should be keyed by (agent, OS) with `%USERPROFILE%`/`%APPDATA%`/`%ProgramData%`/`C:\Program Files` substitutions, and a WSL scanner that enumerates distros' home folders from Windows (or runs a small helper inside WSL) because agents installed inside WSL keep their own `~/.claude`, `~/.codex`, etc.
- Linux credential handling is weakest (plaintext `.credentials.json` for Claude; libsecret only where a keyring daemon runs), so "credential file is world/group-readable" and "plaintext token fallback in use" checks matter most there.
- Windows: no Claude sandbox natively and writer attribution requires admin ETW; position Windows as "inventory, diff, secrets, billing lint, hooks" without attribution in v1.

### Gaps
- VS Code/Cursor user-data paths per OS were not re-verified in this pass.
- Windows Credential Manager target names used by Codex, Copilot and Claude (if any) were not found.
- WSL interop details (accessing `\\wsl$` from a Windows service, performance of watching it) were not researched.

## 10. Synthesis: capability feasibility table and recommended MVP architecture

### Takeaway
A useful guard is buildable by one developer today if it is scoped as "local inventory + semantic change history + secret and capability lint + billing lint + optional cooperative hooks", with honest "probable writer" attribution; true attribution and blocking of config writes (Endpoint Security), MCP gateways, and account-side billing reads should be deferred because they need Apple approval, root, or credential reuse that conflicts with vendor terms.

### Cited Findings
- Writers are invisible to FSEvents/inotify/ReadDirectoryChangesW; ES needs entitlement + root + FDA; fanotify needs privileges for pid — [Apple FSEvents](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/TechnologyOverview/TechnologyOverview.html); [es_new_client_result_t](https://developer.apple.com/documentation/endpointsecurity/es_new_client_result_t); [fanotify_init(2)](https://man7.org/linux/man-pages/man2/fanotify_init.2.html); [FILE_NOTIFY_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-file_notify_information)
- Hooks that deny exist in all target agents, with fail-open defaults in several — [Claude Code hooks](https://code.claude.com/docs/en/hooks); [Codex hooks](https://learn.chatgpt.com/docs/hooks); [Cursor hooks](https://cursor.com/docs/agent/hooks); [Copilot hooks reference](https://docs.github.com/en/copilot/reference/hooks-configuration); [Gemini hooks](https://geminicli.com/docs/hooks); [OpenCode plugins](https://opencode.ai/docs/plugins/)
- Permissively licensed secret engines exist (MIT/Apache) — [gitleaks](https://github.com/gitleaks/gitleaks); [Kingfisher](https://github.com/mongodb/kingfisher); [BleepingComputer on Betterleaks](https://www.bleepingcomputer.com/news/security/betterleaks-a-new-open-source-secrets-scanner-to-replace-gitleaks/)
- No permissions manifest for MCP servers — [MCPB manifest](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md); [server.json](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/server-json/generic-server-json.md)
- Account-side billing switches live only in vendor dashboards — [Claude Help: usage credits](https://support.claude.com/en/articles/12429409-manage-usage-credits-for-paid-claude-plans); [OpenAI Help: credits](https://help.openai.com/en/articles/12642688-using-credits-for-flexible-usage-in-chatgpt-freegopluspro); [Cursor spend limits](https://cursor.com/docs/account/billing/spend-limits)

#### Recommended MVP architecture (deliverable 4)
1. **Rust core (`guardd`) as a per-user background agent** (LaunchAgent via `SMAppService` on macOS; later a systemd user unit and a Windows per-user startup task), exposing a local IPC/HTTP API on loopback with a per-install token; thin UI shell (Swift menu bar for macOS v1, or Tauri 2 if Windows/Linux are in the first release, per earlier note section 9).
2. **Adapter registry** (data-driven: agent, OS, path patterns, format, security-relevant key paths, known benign writers). Ship adapters for Claude Code, Codex, Cursor, Copilot CLI, VS Code, Gemini CLI/Antigravity, OpenCode, Claude Desktop; read `CLAUDE_CONFIG_DIR`/`CODEX_HOME`/`COPILOT_HOME`/`GEMINI_CLI_HOME`-style overrides from the user's shell env.
3. **Watcher + differ**: FSEvents file-level stream on enumerated directories (not `$HOME`), 1 to 2 s debounce, SHA-256 per file, format-aware parse and key-path diff; whole-file hashes only for low-churn files; never parse transcripts by default.
4. **Baseline store**: SQLite (append-only change log + current snapshot), records HMAC'd with a Keychain-held key; "accept change" workflow that updates the baseline; export of signed digests.
5. **Attribution heuristics**: process snapshot at event time (executable path, parent chain, code-signing team ID where readable), agent session windows (Claude `~/.claude/sessions/` lock files, optional hook-fed SessionStart/End), known-manager allowlist (cc-switch, ToolHive, MCPM), and labels: "expected", "agent was running", "no owning app running", "repository change after git pull". Present as "probable writer" with confidence, IAXT-style.
6. **Analyzers** (pure functions over parsed config): secrets (embedded MIT/Apache rules, fingerprints, no live verification), capability/static risk (launcher class, pinning, provenance, dangerous patterns in hooks/scripts, HTTP hooks to non-loopback, `trust: true`, `allowed-tools`, bypass/YOLO settings, `enableAllProjectMcpServers`, new allow rules), and billing lint (B1 to B8, B12 to B14).
7. **Repo pre-flight**: scan a folder for agent config files when it appears (new clone) or after `git pull` (FSEvents on `.git/HEAD`/`ORIG_HEAD` in watched project roots chosen by the user), before an agent opens it.
8. **Optional enforcement pack (opt-in per agent)**: minimal guard hooks (`PreToolUse`/`UserPromptSubmit`/`ConfigChange` for Claude as an HTTP hook to loopback; Codex `PreToolUse`; Cursor `preToolUse`/`beforeMCPExecution`/`beforeReadFile` with `failClosed: true`; Copilot `preToolUse`; Gemini `BeforeTool`), each pointing at a signed binary in the app bundle, with the watcher verifying their presence. Policies: block reads of credential paths, flagged MCP servers, prompts over a spend cap.
9. **Remediation UX**: guided per-agent fixes with preview diff, backup, vendor-CLI write path where available, connectivity check, and "rotate this key" reminder; never auto-fix silently.
10. **Trust posture**: open-source core and rules, no telemetry, local-only; notarised Developer ID builds; signed updates.

#### What to defer
- Endpoint Security system extension for true attribution and write blocking (apply for the entitlement early; ship later as an optional component). Linux root helper (fanotify/auditd) and Windows admin ETW service likewise later.
- Dynamic MCP tool fetching and description pinning (only as explicit sandboxed action, v2).
- MCP gateway/proxy and LLM base-URL proxy (overlap with Docker/ToolHive/MCP Router; high breakage and trust cost).
- Account-side billing reads via cookies or private endpoints (terms risk); keep as manual checklist.
- LLM-based analysis of tool descriptions/skills (privacy: would send content off-device unless a local model is used).
- Team/fleet features (MDM deployment, central dashboards) where Fleet, GitGuardian and 1Password already operate.

### Gaps
- No prototype was built; ratings derive from documentation and from how existing tools work.
- The bypass questions in Section 5 (hooks under YOLO modes; project-level `disableAllHooks`) need hands-on testing before any "protection" claim.
- ES approval odds for an individual developer in 2026 remain unknown.
